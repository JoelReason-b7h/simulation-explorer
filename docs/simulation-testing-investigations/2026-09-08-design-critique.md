# Review: `docs/simulation-testing-direct-model.md` — against the code, with concurrency as a hard V1 requirement

Repos read: `/home/user/exchange` (core, clearing, ops-api, simulator-api, public-api/direct, test-e2e, performance-testing) and `/home/user/api-docs-portal/specs/openapi-v1.yml`. Line references are to those trees.

## Wrong — factually incorrect claims

**W1. "Every direct platform is POOLED" is not true of the code or of the test corpus, and four of the document's structural decisions rest on it.**
Evidence: `CustomerCreationStrategyFactory.java:77-84,113-121` selects among `directEntityModelStrategy` (direct+INDIVIDUAL) and `pooledEntityModelStrategy` (direct+POOLED); `ScheduleEventType.java:268-270` carries the comment "Transfer type describes Trust-model money movement and says nothing about how a Direct Model platform operates ... whichever way it happens to be set (SAV-11158)". The direct feature corpus declares **38 INDIVIDUAL/UNVERIFIED vs 29 POOLED/VERIFIED** direct platforms (`features/order/direct/**`, e.g. `customer_notice_deposit_and_withdrawal.feature` scenario 1 is INDIVIDUAL and asserts `depositInfo`). The simulator exposes the per-account rail: `SimDirectPaymentOperations.addDirectCustomerTransaction` (`/simulator/direct/payment/customer/{customerUid}/accounts/{accountId}/transactions`). What *is* true: batches are POOLED-only (`DirectBatchOrderHandler.java:134,392,405` `validateTransferType(..., POOLED)`). So "POOLED" is a fact about which production tenant you care about (Investec), not about the system. Consequences the doc draws that fall with it: `depositInfo` "always null" (only for POOLED), "the pooled rail is the only funding rail", ISA "impossible", and `transferType` "an environment constant". Under the new many-platforms requirement this matters more, not less: the harness can and arguably should run INDIVIDUAL and POOLED direct platforms side by side, since the corpus does.

**W2. "The customer must be ACTIVATED before any deposit settles" and "KYC decides off the last name" hold only for `UNVERIFIED` onboard type.** `CustomerCreationStrategyFactory.java:78-81`: `isVerified ? verifiedKycStrategy : ...` — a `VERIFIED` platform skips the KYC fake entirely. 29 of 30 POOLED direct platforms in the corpus are `VERIFIED` and use names like `'Pool Notice'`, `'Set Cust A'` with no `pass`. The §8 rule "a neutral last name silently strands every journey" is therefore false on the platform shape the doc targets. The fake also has more levers than `pass` (`DefaultCheckResponseProcessor.java:33-63`: `sanc` → sanction TRUE_MATCH, `idv` → IDV INCONCLUSIVE, `advm` → adverse media INCONCLUSIVE) — those are the cheap route to FROZEN/DEACTIVATED/pending states, and the doc does not know they exist.

**W3. Target A is already tested, verbatim.** §9 says "the API documents the rule while nothing obviously tests it". `features/order/direct/dm_batch/batch_match_by_reference_set_settled_by_two_payments.feature` is exactly Target A (two batches sharing `PAYSET`, 50 then 50; neither settles after the first, both after the second). Siblings cover the mismatch-held case (`..._two_payments_mismatch_held`), one batch funded in tranches, and unmatched. There are 16 `dm_batch` features. The coverage-subtraction metric in §6 would have caught this — do that indexing *before* choosing targets.

**W4. "Crons fire on wall-clock time regardless of the injected clock" is only half true, and the half that is false undermines the "run both ways" experiment.** The `@Scheduled` *tick* is wall-clock, but the batch framework decides what is *due* from the injected clock: `BankScheduleExecutor.java:30` and `PlatformScheduleExecutor.java:30` tick `* * * * *`, then `BankScheduleManager.java:38` → `PartnerSchedulingRepository.selectAndReserveCurrentBankEventSchedules(timeProvider.getInstant())`, whose SQL is `WHERE next_raised <= ?:endRange AND status IN ('COMPLETED','FAILED')` (`:119-130`). On any environment where scheduling is enabled, a `SetClock(+1d)` fires *every* due bank and platform event within 60 s — for a POOLED platform that includes `DEPOSIT_PAYMENT_DUE`, `WITHDRAWAL_PAYMENT_DUE`, `DISTRIBUTION_PAYMENT_DUE` (`ScheduleEventType.java:265-266,339-341`), and for the bank `ACCRUALS_AND_REALISATIONS`, `BANK_ORDER_PAYMENT_DUE`, etc. So `RaiseBankPaymentDue`/`RaiseCustomerPayout` cannot be "left off" to see if the payout still completes — the executor raises them for you. Also `/ACCRUALS_AND_REALISATIONS/sync` can collide with the executor's own reservation (`status = 'RUNNING'`) of the same row.

**W5. The classification of ops calls into "genuinely required" vs "latency shortcut" is wrong for the local stack, probably in the opposite direction.** `scripts/launch_stack:6-9` forces `MICRONAUT_ENVIRONMENTS=acceptance`; core and clearing acceptance profiles both set `b7h.async.scheduling.enabled: false` (`core/application-acceptance.yml:68-70`, `clearing/application-acceptance.yml:25-27`). No consumer of that property exists in this repo — it is read by the external `b7h.libs.micronaut` shedlock aspect (every scheduler above carries `@SchedulerLock`), so I could not prove it disables them, but every one of the 65 direct scenarios invokes each job explicitly and none ever waits on a cron. If scheduling is off locally: `SendPayments`/`SettleBankCredit` are *required*, "waiting ≤60 s produces a journey that looks like a real integrator's" never happens, and the W4 catch-up does not occur locally but *will* on dev/sandbox/preprod, which §10 explicitly targets. Verify with one grep of a local core log for `Invoking send external requested payments job`.

**W6. "Receiving webhooks is trivial locally" — the e2e code says the opposite.** `ExternalDirectWebhookSubscription.java:23` `@Pattern("^https://.+")`; `Webhooks.java:214-231` javadoc: "Subscribing over the public API therefore either fails validation (http) or fails TLS on delivery (https) — which is why direct webhooks have never actually been delivered in acceptance." The corpus subscribes direct platforms through the **ops-api** (`opsPortalWebhookClient.createPlatformWebhook`), not the four public webhook operations the doc plans to use at setup. The harness needs a TLS listener with a cert the core container trusts, or the ops route. Also the wire value is `VERSION_1` (`ExternalDirectWebhookVersion.java:5`, spec enum `WebhookVersion: [VERSION_1]`); "1.2" is the internal name the e2e steps use and would be a 400 on the public API.

**W7. `SettleBankCredit` is not what settles the simulated credit.** `SimDirectPaymentController.makeTransaction` → `TransactionSettlementSimulationClient.sendTransactionSettled` → `TransactionSettlementSimulationService.java:32-34` publishes a `TransactionSettled` straight onto the clearinghouse queue. No statement line is booked at hot-sauce-bank; the HSBC `poll` is irrelevant to the inbound credit (it confirms outbound DBITs). What the corpus does after a pooled credit is `transactions/process` (drain) then `SAFEGUARD_HUB` aggregation and a *further* send/process leg (`customer_notice_deposit_and_withdrawal.feature`, pooled scenario) — a leg missing from Target B. Relatedly, the sentence "a clock set to 03:00 makes `SettleBankCredit` required because there is no poll" contradicts the doc's own wall-clock point: the `6-23` window is the cron's, i.e. wall-clock.

**W8. Smaller factual slips.** 359 feature files, not 361. `CustomerPaymentDueProcessor` (`:29`) raised *customer* deposit dues via `CustomerDepositPaymentDueRaisingService`, not the platform `DEPOSIT_PAYMENT_DUE` job; its deprecation is not evidence about `RaiseCustomerPayout`. `CancelBatchDeposits` (`DELETE /direct/v1/batches/{batchId}`) requires a body (`CancelBatchRequest {cancelAll, instructionIds}`) — the catalogue lists it as a bare delete.

## Won't work — plausible designs that fail on contact

**N1. "Many simulated platforms at once" is blocked by auth before anything else.** One Cognito `client_id` maps to exactly one platform (`ClientLinkRepository.java:77-83` `Optional fetchByClientId`; `platform_client_link`); the local stack has two real client IDs (`AuthenticationHelper.java:29-30`); the simulator resolves *which* platform to credit from the caller's token (`SimDirectPaymentController.java:59` `identityProvider.get().getPartnerUid()`), so `SimulatePlatformCredit` must be called with the platform's own token too. N platforms means N Cognito app clients (real ones — the JWKS is real Cognito's, served from wiremock, `public-api/application-acceptance.yml:6-13`) or a local token issuer. This is the week-1 stall.

**N2. `SetClock` does not reach the JVM the harness reads from.** Direct API reads go through `*ReadOnlyClient` → `savings-exchange-readonly` → `core-ro:4001` (`docker/public.env:2`; `DirectIdentityProvider`/customer/product controllers all inject RO clients). `setClock` is sent to `core:4000` only (`OpsPortalSetupController.java:71-73`); `timeProvider.set()` is per-JVM ("set() has no effect on the production clock", `SetupController.java:100`). So the projector's snapshots are computed at wall-clock while the writer is 33 days ahead — `projectedMaturityValue` (`DirectMaturityEstimation`), `DirectAccountValidator.java:98`, `nextInterestRealisationDate`, `topUpDeadline` and anything else derived on read will disagree with the write side. The doc says three services; there are four clocks, and the e2e suite never sets the fourth either.

**N3. Global operations that make journeys interfere (Q1).** Beyond the ones you listed:
- `BankScheduleExecutor`/`PlatformScheduleExecutor` — one `@SchedulerLock("BankSchedulerService")`, `@Named("singleTask")` executor: every bank's jobs serialise on one thread, and after any clock move everything due fires (W4).
- `DirectNoticeWithdrawalOperations.processDueNoticeWithdrawals(today, now)` (`:72`) — no bank parameter; repository is `due_date <= ?:dueDate` across the table (`DirectCustomerAccountNoticeRepository.java:63`).
- `DirectAccountClosureOperations.processAllAccountClosures()` (`:237-250`) — sweeps every CLOSING account in the world.
- `PaymentDueAggregationService.aggregateAndSettleExternalPaymentDues()` (`:67-68`) — global sweep, per-account-owner aggregation; `payment/groups/process` and `statement/transactions/process` drain shared queues. Correctness is per owner; attribution is not.
- `TestEnvironmentTransactionFundingService` + `AutomaticFundingScheduler` (`*/10`, gated by `b7h.feature-flag.sim-automatic-withdrawal-funding.enabled`, not set in acceptance — check dev/sandbox) autofunds *everyone's* BANK_HUB and PLATFORM_SAFEGUARD dues behind the harness's back; also exposed as `/operations/processor/fund/{deposits,withdrawals}`.
- Preloaded pool: claim is `FOR NO KEY UPDATE SKIP LOCKED LIMIT 1` on the exact four-tuple (`InternalAccountRepository.java:60-69`) — race-safe, so it is an *exhaustion* point shared by all platforms, not a correctness one. `InvestecAccountAutoPreloadScheduler` exists but is flag-gated off in acceptance.
- `HsbcAccountStatementPollingScheduler.resetPollingPeriods` (`:84-93`) resets poll windows at *injected-clock* midnight — a clock jump across midnight resets everyone's polling state.
- Reference matching is scoped to the receiving virtual account (`PaymentDueForMatchingRepository.java:44` `ia.account_uid = ?:criteria.accountUid`), so per-platform isolation *does* hold there; collisions on `paymentReference` (`^[a-zA-Z0-9]+$`) are intra-platform and the harness's own.

**N4. Attribution and poisoning of the learned relation (Q3).** Per-platform isolation contains customer/account/batch state, matching, aggregation and webhooks. It does **not** contain: the clock (global, and split per N2), the notice sweep, the closure sweep, the send/process queue drains, pool exhaustion, and — if platforms share the "Direct Bank" — interest and every bank-scoped job. A journey that records `(state, SendPayments) → payout completed` has learned nothing if another journey's `SendPayments` did it. My read: isolation is necessary but not sufficient; the fix is structural. Stop treating global world actions as *journey* actions. Run them on a single shared ticker as *epochs*, record "world epoch advanced" against every live journey, and learn transitions only from tenant actions plus epoch boundaries. Attribute effects by the causality tokens the API already hands you — `instructionReference`, `batchReference`, `paymentReference`, `Idempotency-Key` echo, webhook payload ids — not by temporal adjacency. Give each platform its own bank so interest/notice/closure blast radius is per platform where the code allows it (notice and closure do not — those stay epoch-only).

**N5. The weak invariants under concurrency (Q2).** The five in §7 are single-entity monotonic properties and remain *valid* concurrently; they just stop discriminating money loss, as the doc says. The metamorphic one — "another customer's actions never change this customer's observable state" — is **false by design** on this system (shared `paymentReference`, `account_cancel_reduces_shared_batch.feature`, bank-wide notice, global closure) and will fire constantly; scope it to different platforms. Minimum replacement, and yes it is computable over the wire: (a) per account, `balance == Σ CREDIT − Σ DEBIT` over `GET …/accounts/{id}/transactions` (`amount`, `mark`, `type` incl. `INTEREST`); (b) per customer, `Σ account balances + unallocatedCashBalance == totalBalance` (`BalancesResponse`); (c) per batch, `Σ accepted allocations == totalPaymentRequired` decreasing to 0 at SETTLED. The one that needs more than the Direct API is the platform pot: held groups for FROZEN customers and cancelled groups keep money "in the platform cash pot" (`DirectPlatformAccountHandler.java:240-253`) where it is neither a customer balance nor `unallocatedCashBalance`. That needs the platform VA balance via ops-api — still HTTP, no DB — or conservation will report leaks that are holds.

**N6. Per-bank logical date will leak on the direct paths (your specific ask).** `BankDateProvider` is consumed by `DirectModelInterestProcessing`, `CustomerProductAccountInterestRealisationService`, `DirectDataReconService` and little else. Global-clock reads on the INSTANT/NOTICE paths: notice due date stamped from `timeProvider.getLocalDate()` (`NoticeProductService.java:72,82`) and swept with `timeProvider.getLocalDate()` (`DirectNoticeWithdrawalScheduler.java:37`) — both ends; `DirectCustomerInstructionService` (9 `getInstant()` sites — instruction `createdAt`); `DirectAccountValidator.java:44,98` (T&C not-in-future, maturity vs today); `DirectBatchOrderHandler`, `DirectAccountClosureOperations:201`, `DirectPlatformAccountHandler`, `DirectMaturityEstimation`, `DirectDepositSweepService`, `DirectWithdrawalEgressService`; and the batch framework itself decides bank-job dueness from the global instant, not the bank date (`selectAndReserveCurrentBankEventSchedules(timeProvider.getInstant())`). Clearing has no bank-date concept at all — payment-due dates, the simulated settlement timestamp (`TransactionSettlementSimulationService.java:44`), poll windows and maintenance checks all read clearing's global clock. A partition in core is invisible to clearing.

**N7. Binding by name is fine for path params; body construction is where journeys die silently.** `CustomerRequest` needs a valid `nino`, UK `phoneNumber`, `GBR` address, `customerTaxResidencies` that must not be `GBR`, `fscsAcknowledgedAt` not in future, `dateOfBirth` ≥ 18y, `isVulnerable`/`vulnerableDescription` coupling — none derivable from the spec beyond `required`. `BatchPaymentAllocation` needs `productId` (bound from `GET /products`, fine), `accountReference` (from the account, fine), and `instructionReference`/`batchReference`/`customerReference` which are *generated uniques* the harness must own. The silent-dead-journey cases: `AccountOpeningRequest.amount` below product minimum (batch settles to `unallocated_cash` via `BELOW_PRODUCT_MINIMUM`, looks like a finding, is a generated-value artefact); a WITHDRAW on a pooled customer with no nominated account is rejected (`ExternalApiDirectAccountController.java:169-170`); `CancelInstruction` is legal only for `WITHDRAWAL` on `NOTICE` in `PENDING` (`:232-233`), so the §7 "cancel-then-reissue" metamorphic check is NOTICE-only.

**N8. Replay against a stateful system.** Every replay re-mints `customerReference`, `batchReference` (409 on reuse, `DirectBatchOrderHandler.java:141-143`), `instructionReference`, `paymentReference`, `Idempotency-Key`, and a new preloaded account; a "route back to a rare state" is a fresh set of entities that reaches an *isomorphic* abstract state, not the same one — fine for visit counting, useless for "resume this journey after 30 days". The persistence story in §5 (stored rows with due dates) is the right one for the latter, but it is incompatible with `SetClock` being global: you cannot park journey A at day 3 while journey B advances the world to day 33.

## Missing — should be there and is not

**M1. Abstract state has no subject.** §2 lists facts but never says what the tuple is *of*. With N customers × M accounts × K batches per journey the key must be per-entity (account-level, joined to its customer status and product type), with journey-level aggregates as separate counters; otherwise Target A (two customers, two batches, one reference) collapses into one bucket with "one customer, one batch".

**M2. States the projector will meet and does not know:** `DirectInstructionHoldType.DEPOSIT_POOLED` (frozen customer's deposit held in the pot, released on unfreeze); cancelled groups leaving funds in the pot; `PAYMENT_PENDING_ALLOCATION` reasons `NO_ASSOCIATED_REQUEST` vs `BELOW_PRODUCT_MINIMUM`; account closure driving a *system-initiated* full-notice withdrawal (`DirectAccountClosureOperations.java:193-223`); `NominatedAccountVerificationState` and CoP (`BankAccount.accountName` required when CoP is on).

**M3. Quiescence.** Every mutation crosses SQS/JMS (`ClearinghousePublisher`, `DirectPlatformAccountHandler`) and `AFTER_COMMIT` listeners; the doc's fixed waits come from a scenario player. Under concurrency, "settle" must be per-entity (poll until the entity's own diff is stable over two reads and its causality token appears), not per-action.

**M4. `moveBankBusinessDate` semantics.** `SetupController.java:104-107`: `true` sets every bank's `BankDateProvider` to the clock's date. With per-bank dates now central, the harness needs to decide who owns the bank date — interest processing (idiom passes `false`) or the clock action — and never both.

## Fine, actually

- All cron expressions cited: `0 0 3 * * *`, `0 9-17 * * MON-FRI`, `* * * * *`, `*/5 6-23 * * *` (both) — exact.
- Spec counts: 31 ops, 22 paths, 115 schemas, 7 path params with the stated use counts; the six enum lists; `paymentReference` shared-reference text is quoted correctly (`BatchPaymentRequest.paymentReference`).
- `SetClock` → core + clearing (`OpsPortalSetupController.java:71-73`), hot-sauce-bank set separately (`Setup.java:336-339`); interest idiom = `+1d 06:00, moveBankBusinessDate=false`, then `ACCRUALS_AND_REALISATIONS/sync` (`ScheduledJobSteps.java:97-108`, `Scheduler.java:143-146`).
- `PlatformDepositPaymentDueRaisingService.instructionDirection() == EMONEY_HUB` (`:69-71`); `api-order-v2.enabled: true` in acceptance; `CustomerPaymentDueProcessor` `@Deprecated(forRemoval=true)` gated off by that flag.
- The "doubtful for direct" hypothesis is well-founded: direct payout dues (`CASH_ACCOUNT_CUSTOMER`) are created inline in clearing (`CashAccountWithdrawalService.java:66-67`), not by `DEPOSIT_PAYMENT_DUE`; `raiseBankPaymentsDue`/`raiseCustomerPaymentsDue` are exactly as described (`PaymentDue.java:81-105`); `longAwaitWithActionUntil` shape is as described (`PaymentDueSteps.java:139-142`). Just note W4: you cannot test it by omission on a scheduler-enabled environment.
- Pool preload four-tuple, no fallback — correct (`InternalAccountRepository.java:60-69`); `TimeTravel` is DB mutation; `ledger.py`, `docs/authoring/*`, both postman dirs exist; the quoted `direct-vs-trust.md:36` line and `domain-gotchas.md` ACTIVATED rule are real; `initiating-payments.md` waits (10 s / 2 s / 8 s) and the `BANK_ORDER_PAYMENT_DUE` no-op note are real.
- Named feature files all exist at the paths I found (`dm_withdrawal/…`, `dm_customer_onboarding/…`, `dm_notice_deposit_and_withdrawal/…`, `customer/customer_create_replays_on_duplicate_idempotency_key.feature`); 12 `frozen_*` features.

## Where it stalls

- **Week 1:** N1. One token = one platform; the simulator credits the token's platform. Nothing concurrent runs until there is a per-platform credential story. Second blocker the same week: W6 — no webhooks arrive over the public API locally, so the "webhooks double as quiescence signal" plan is dead until a TLS receiver or the ops subscription route is in place.
- **Week 3:** N2 + W4/W5. The first `AdvanceDays(33)` produces reads that disagree with writes (core-ro on wall-clock) and, on dev/sandbox, a burst of auto-fired batch jobs the driver did not request; locally, nothing moves unless every world action is explicit. Each looks like a system bug and is not.
- **Week 8:** N4. The learned relation has thousands of edges caused by other journeys' world actions and epoch changes; nobody can say which findings are real. That is the point where the outside-in framing gets abandoned for a declared model — the outcome the document was written to avoid — unless world actions were epochs from day one.
