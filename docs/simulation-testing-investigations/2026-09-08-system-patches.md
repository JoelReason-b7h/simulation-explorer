# Investigation: system patches to enable the direct-model simulator

Verbatim output of a background investigation run on 2026-09-08 (Fable 5.1), briefed to propose
small, high-leverage changes to the production system that would make the harness described in
`docs/simulation-testing-direct-model.md` easier to build and more powerful. Driven by the
requirement that the harness run many simulated platforms concurrently.

Recorded unedited. Line references are to the tree as of this date. Cross-check before acting —
one finding (`depositInfo`) is explicitly flagged by the author as needing empirical verification.

---

# Findings and ranked patch proposals

## Two headline verifications

**1. The direct auth client binding is real, but the folklore has the direction wrong.**
- `platform_client_link` has `UNIQUE (client_id)` and `UNIQUE (platform_sid)` (`/home/user/exchange/apps/savings-exchange/core/src/main/resources/db/baseline/V20260508160933__baseline.sql:19686, 19702`). One client resolves to exactly one platform, full stop.
- Non-prod direct platform creation auto-links the single shared `direct-model-test-clientId` (`.../core/service/PartnerPlatformService.java:238-245`; value in `.../core/src/main/resources/application.yml:95`). The upsert is `ON CONFLICT (client_id) DO UPDATE SET platform_sid = <new>` (`.../port/persistence/sql/ClientLinkRepository.java:26-39`) — so the shared client follows the **newest** platform, and the previous platform is left with no link at all. `direct-vs-trust.md:14-19` says "first"; the code says "last".
- Why it looks like "first": public-api caches the resolved `Authentication` per JWT hash until half the token's TTL (`/home/user/libs/micronaut/micronaut-security/auth/cognito/.../CognitoJWTAuthenticationFactory.java:74-77`, `AuthCognitoCacheExpiry.java:35`). A token minted before the second platform was created keeps resolving to the first.
- Tokens are real dev-pool Cognito client-credential tokens (`/home/user/exchange/tools/test-e2e/src/main/java/b7h/tools/e2e/auth/AuthenticationHelper.java:38, 61-66`; the DIRECT profile reuses the POOLED app client). So N concurrent direct platforms need N Cognito app clients. That is the real ceiling, not code.

**2. Logical time is already per-bank for accruals; it leaks only on the notice path, and payouts do not depend on it.**
- Confirmed: `BankDateProvider` with `DatabaseBankDateProvider` as the default (flag `logical-accrual-date.enabled` defaults `true`, `application.yml:300-301`; `RealTimeBankDateProvider` only when explicitly `false`, `.../core/config/bank/RealTimeBankDateProvider.java:12`). A bank's date row is created at approval (`.../core/service/PartnerBankDecisionService.java:121-122`).
- Direct accrual reads only the bank date and **self-advances**: `ProductAccountInterestProcessor.java:28-33` → `DirectModelInterestProcessing.execute` (`:59-67`) does accrue → `setNextBusinessDate` → realise. `TimeProvider` appears in that path only as `lastProcessedAt`/`created_at` stamps (`CustomerProductAccountInterestAccrualService.java:82`). Consequence: **`AdvanceDays(n, bank)` is n calls to `/bank/{bankUid}/ACCRUALS_AND_REALISATIONS/sync` with no `SetClock` at all.**
- `nextDay` side effect: `incrementBusinessDateAndQueueEODReport` inserts one `customer_product_account_eod_stats_run` row per tick (`.../account/interest/BusinessDateRepository.java:38-54`). One row per simulated day per bank; harmless in volume, but it is a queued report job — expect the consumer to run.
- **The leak:** notice due dates are computed from the global clock at placement (`.../core/NoticeProductService.java:79-88`, `timeProvider.getLocalDate()`), and both the scheduler and the ops endpoint compare against global today (`.../schedulers/DirectNoticeWithdrawalScheduler.java:36-40`; `.../port/restapi/core/processor/CoreProcessorController.java:194-198`). The sweep SQL has no bank or platform predicate (`.../core/direct/DirectCustomerAccountNoticeRepository.java:34-65`). Without a patch, a bank whose date has been advanced 33 days still has no due notices.
- **Payouts do not stall:** direct payment dues are stamped `dueDate = timeProvider.getInstant()` (`.../core/direct/PaymentDueDirectCustomerAccountService.java:~115` into `PaymentDueToRaise.dueDate`, `.../payment/due/model/PaymentDueToRaise.java:29`); clearing stamps internal transfers with its own `timeProvider.getInstant()` (`.../clearing/core/payment/model/v2/draft/DraftPaymentDue.java:76, 118`) and aggregates with `due_date <= timeProvider.getInstant()` (`.../clearing/.../PartnerPaymentDueRepository.java:254-260, 302-310` via `PaymentDueService.java:197-199, 221-222`). Everything is "now" on both sides, so per-bank date partitioning never blocks a payment.
- Two things the design doc gets wrong that matter here: (a) `SetupController.setClock` with `moveBankBusinessDate=true` overwrites **every** bank's date with the global one (`.../port/restapi/core/setup/SetupController.java:98-109`) — it destroys the partition; the e2e `Migration.setTime` always passes `true` (`tools/test-e2e/src/main/java/b7h/tools/e2e/workers/Migration.java:42`). (b) "crons fire on wall-clock regardless of the injected clock" is half true: the every-minute poller is wall-clock (`BankScheduleExecutor.java:30`), but which schedule rows it fires is decided by `timeProvider.getInstant()` (`BankScheduleManager.java:38`; reserve SQL `PartnerSchedulingRepository.java:~123-127`). Every approved bank gets a daily 00:00 `ACCRUALS_AND_REALISATIONS` row (`PartnerBankDecisionService.java:128-141`; `ScheduleEventType.java:123-130`), so a global clock jump fires them.

## Ranked patches

### 0. Zero-code affordances the harness should adopt first
Not patches, but they change what the patches need to do.
- **Per-cohort bank, date advanced by accruals only.** Create one direct bank per cohort; advance with `POST /operations/batch/processor/bank/{bankUid}/ACCRUALS_AND_REALISATIONS/sync` (`.../ops-api-common/.../OpsPortalBatchFileProcessorOperations.java:47-50`; `sync` runs inline, `ScheduledEventController.java:98-101`). Never call `SetClock` with `moveBankBusinessDate=true`.
- **Disable the auto-tick per bank.** `POST .../bank/{bankUid}/ACCRUALS_AND_REALISATIONS/status` with `jobStatus: DISABLED` (`OpsPortalBatchFileProcessorOperations.java:64-69`; `JobStatus` has `DISABLED`; reserve SQL only picks `COMPLETED`/`FAILED`). Then only the harness advances that bank's date.
- **Multi-platform without code, up to the number of Cognito app clients:** create platform N+1 (shared client moves to it, platform N is unlinked), then `POST /operations/platforms/integration-partner`-style `createIntegrationPartner(platformN, <distinct app client id>, <random sharedKey>)` (`OpsPortalPlatformController.java:77-79` → `PlatformController.java:82-90`). This works precisely because `linkApiClient` only honours the supplied id when the platform has no link (`ApiAccessService.java:45-51`). Mint a fresh token after relinking (cache is per JWT hash).
- **Webhook quiescence already exists:** `GET /operations/webhook/events?platformUid=&eventState=AWAITING_RESPONSE` (`.../operations/webhook/OpsPortalPlatformWebhookOperations.java:21-22`; SQL `PlatformWebhookEventRepository.java:90-118`).
- **Queue depth:** LocalStack SQS `GetQueueAttributes` (`ApproximateNumberOfMessages{,NotVisible}`) on the queues in `application.yml:219-261`. Stack-wide, not per partner, but free.
- **Startup precondition to add to §8:** `TimeProviderFactory` hands out the settable `OffsetTimeProvider` **only** when `b7h.env == acceptance` (`/home/user/libs/time-utils/time-injection/.../TimeProviderFactory.java:21-27`); otherwise `CoreTimeProvider.set` is a silent no-op. Assert `SetClock` round-trips before trusting it.

### 1. Scope the notice sweep by bank and accept an explicit as-of date — **highest payoff**
- **Change:** add `@Nullable @QueryValue BankUid bankUid, @Nullable @QueryValue LocalDate asOf` to `processDueDirectNoticeWithdrawals` in `.../exchange-core-common/.../CoreProcessorOperations.java:60` and `.../ops-api-common/.../OpsPortalProcessorOperations.java:128`, thread through `CoreProcessorController.java:194-198` (default `asOf` to `bankDateProvider.getDate(bankUid)` when a bank is given, else today as now) and the ops-api implementation, add `bankUid` to `DirectNoticeWithdrawalOperations.fetchUnprocessedNoticeWithdrawalsDueOnOrBefore` (`:65-68`), and one predicate in the repository SQL, which already joins `partner_bank pb`: `AND (?:bankUid::uuid IS NULL OR pb.uid = ?:bankUid)` (`DirectCustomerAccountNoticeRepository.java:34-65`). PG14-safe.
- **Size:** ~25 lines, 5-6 files. Purely additive; existing callers (scheduler, current ops call) unchanged.
- **Unlocks:** the whole per-bank time partition becomes usable for NOTICE — Target B runs with zero global clock movement. Removes the last reason for `SetClock` in V1.
- **Risk:** none to production paths. Note a latent hazard it *reduces*: `processDueNoticeWithdrawals` fetches outside a transaction then raises in `@Transaction(exclusive = true)` (`DirectNoticeWithdrawalOperations.java:70-95`) — `exclusive` means "throw if nested" (`/home/user/libs/persistence/persistence-api/.../PersistenceContext.java:23`), not a lock. The ops endpoint is not under the scheduler's `@SchedulerLock`. Two concurrent unscoped sweeps both see the same rows; the second hits `dci_pdt_unique` (`.../db/migration/V20260803110202__unique_payment_due_per_direct_instruction.sql`) and rolls back its **entire** batch. Bank scoping keeps cohorts from colliding; the harness must still serialise within a bank.
- **Optional, production-behaviour change, flag it:** compute the notice maturity in `placeNoticeWithdrawal` (`DirectNoticeWithdrawalOperations.java:55-63`) from `bankDateProvider.getDate(bankUid)` instead of `timeProvider.getLocalDate()`. Coherent (all direct dates in bank-time) but changes due dates in the window between midnight and the accrual run. Not needed if (1) lands.

### 2. Scope the closure sweep by platform
- **Change:** optional `platformUid` on `processDirectAccountClosures` (`CoreProcessorOperations.java:63`, `OpsPortalProcessorOperations.java:134`, `CoreProcessorController.java:201-204`), `DirectAccountClosureOperations.processAllAccountClosures()`/`fetchAccountsReadyForFinalisation()` (`:246-262`), and `AND (?:platformUid::uuid IS NULL OR ppl.uid = ?:platformUid)` in `fetchClosingAccountsReadyForFinalisation` — `FROM_CLAUSE` already joins `partner_platform ppl` (`DirectCustomerAccountRepository.java:51, 119-130`).
- **Size:** ~15 lines, 5 files.
- **Unlocks:** attribution — a cohort's `ProcessDirectAccountClosures` only moves its own accounts, so the observed diff is its own.
- **Risk:** none; `closeAccount` already takes a blocking lock and re-checks `CLOSING` (`:266-280`), so the unscoped version is concurrency-safe — this is about isolation of observation, not correctness.

### 3. Per-bank business-date get/set endpoint
- **Change:** `@Get`/`@Post("/bank/{bankUid}/business-date")` on `SetupOperations` (`.../exchange-core-common/.../SetupOperations.java:22-24` sits next to `/time`), implement in `SetupController` via `bankDateProvider.getDate/setDate`, mirror on `OpsPortalSetupOperations.java:36-37` and `OpsPortalSetupController.java:68-74` delegating through `SetupClient` (declarative `@Client` extends `SetupOperations`, `.../exchange-core-client/.../SetupClient.java:6-7`, so the client gets it for free). Guard the setter with the existing `!env.equals("prod")` check used at `SetupController.java:104`.
- **Size:** ~30 lines, 4 files.
- **Unlocks:** aligning a fresh bank's date to a cohort's chosen epoch, recovering a partition after an accidental `moveBankBusinessDate=true`, and reading the date the harness is otherwise blind to (it is not exposed on any response I found).
- **Risk:** jumping the date without running accruals leaves interest schedules behind (accrual processes per business date). Use for alignment, not to skip days.
- Fits below (1) and (2) because with (0) and (1) in place the harness rarely needs to *set* a date; it mostly needs to *read* it.

### 4. Per-platform "outstanding work" read endpoint (core half)
- **Change:** new `@Get("/direct/outstanding")` on `CoreProcessorOperations`/`OpsPortalProcessorOperations` taking `platformUid`, returning counts of: PENDING direct instructions (via the `FROM_CLAUSE` join at `DirectCustomerAccountRepository.java:45-56`), unprocessed `direct_customer_account_notice` rows, `CLOSING` accounts, and `AWAITING_RESPONSE` webhook events (reuse `selectWebhookEvents` filters). Four read-only queries, one record.
- **Size:** ~60-80 lines, 5-6 files.
- **Unlocks:** replaces settle-timeouts for everything core-side. Honest limit: the clearing half (EXPECTED/unsettled payment dues for the platform's accounts, `PartnerPaymentDueRepository` selects already join `account_owner ao`, `:7-14`) is a separate service and DB; without it "quiescent" still means "counts zero on two consecutive reads and the batch/instruction statuses agree". Do the core half first; it covers webhooks, notices and closures, which are the three the harness cannot otherwise see.
- **Risk:** read-only; carry `@Requires(notEnv = READ_ONLY_ENV)` only if it lands on a bean that is already guarded (it should not need it).

### 5. Optional per-request client id for non-prod direct platform creation
- **Change:** an optional `apiClientId` component on `PartnerPlatformRequest` (`/home/user/exchange/common/savings-exchange/api/api-model/.../PartnerPlatformRequest.java:48-96`, record with an explicit secondary constructor — touching it means touching both constructors), honoured only in the non-prod branch at `PartnerPlatformService.java:243-245`: `Optional.ofNullable(request.apiClientId()).orElse(directModelTestClientId)`.
- **Size:** ~10 lines, 2 files, plus the ops-API model change.
- **Unlocks:** removes the create-then-relink dance in (0) and stops platform N-1 losing its link mid-run.
- **Risk:** low — the prod branch (`:239-241`) is untouched and still mints a real Cognito client. It does not lift the ceiling: each id must be a real app client in the dev pool. Lifting the ceiling is infrastructure (provision K harness app clients), not a repo change; the alternative — enabling `apiCredentialsProvider.createApiCredentials` in acceptance — creates clients whose secret is never returned (`createPlatform` returns only `PlatformUid`), so it is not a small patch.

### 6. Docs corrections (no risk, prevents the next reader repeating this investigation)
- `tools/performance-testing/docs/authoring/direct-vs-trust.md:14-19`: replace "binds permanently to the FIRST direct platform" with "one client, one platform; the shared test client follows the most recently created direct platform; a cached token keeps the old binding until half its TTL".
- `docs/simulation-testing-direct-model.md` §1 and §8: `AdvanceDays` needs no `SetClock`; `moveBankBusinessDate=true` is hostile; schedule rows fire on `TimeProvider` time.

## Investigated and concluded not worth patching

- **Per-tenant instant clock.** 545 `timeProvider.get*` call sites across core and clearing `main`, one singleton provider (`OffsetTimeProvider` is a global offset), plus 64 SQL-side `now()`/`CURRENT_DATE` in the persistence layer that no Java override could reach. The bank business date already gives you the partition that matters for INSTANT/NOTICE; do not build this.
- **Scoping payment aggregation.** `PaymentDueAggregationService.aggregateAndSettleExternalPaymentDues` iterates per account under a per-account DB lock (`.../clearing/core/payment/settle/PaymentDueAggregationService.java:66-96`), and the every-minute cron does the same work (`PaymentDueScheduler.java:23`). Cross-partner is harmless and cohorts calling it concurrently serialise on the account lock. Leave it; run one shared "pump" or just wait 60 s.
- **`ACCRUALS_AND_REALISATIONS` "scoped to a bank not a platform".** Bank is the right grain — the business date is a bank attribute. Give each cohort a bank instead.
- **Preloaded internal account pool isolation.** The claim is `FOR NO KEY UPDATE SKIP LOCKED` (`.../clearing/.../InternalAccountRepository.java:60-95`), so concurrent cohorts are safe; the pool is shared by design (keyed on connector/type/currency/wrapper only). It is a sizing problem, already in §8.
- **`batchId` as a typed UID.** Over the wire it is `string/uuid` either way (`ExternalDirectBatchPaymentResponse.java:24`); the harness binds by name. Pure internal tidiness.
- **Replay blockers.** `batch_reference` is unique per `(batch_reference, platform_sid)` (`DirectBatchInstructionRepository.java:49`, 409 at `DirectBatchOrderHandler.java:141-143`); idempotency keys are Redis-scoped `(partnerUid, method, path, key)` with 24 h completed TTL and the flag defaults off (`.../public-api/common/.../IdempotencyService.java:23-25`; `public-api/src/main/resources/application.yml:150-157`). No customer-reference uniqueness found in the baseline. Replay is solved harness-side: fresh platform per replay, or prefix references with a run id. No patch.
- **`depositInfo`.** The code populates it whenever `accountStatus == REQUESTED` regardless of transfer type (`.../core/direct/DirectModelResponseMapper.java:170-179`, passed through at `.../public-api/direct/.../DirectAccountMapper.java:119`). The design doc's "always null for POOLED" needs an empirical check against a REQUESTED pooled account before anyone patches anything. The published spec has no description on the field (`/home/user/api-docs-portal/specs/openapi-v1.yml:4434-4437`); if a doc fix is wanted, it must go on the class-level `@Schema` of `ExternalDirectDepositInfoResponse`, not field-level (CLAUDE.md rule on non-primitive fields).
- **Notice `dueDate` on `ExternalDirectInstructionResponse`.** Would give the harness a target for `asOf`, but it is a public-contract addition (`.../direct-api-common/.../ExternalDirectInstructionResponse.java:8-26` has only `createdAt`/`status`). Additive and cheap, but needs product sign-off — park it; patch (1) with `asOf = bank date` makes it unnecessary for V1.
- **Acceptance-only auth bypass to multiplex one token across platforms.** The env-guard pattern exists (`LocalAuthenticationService.java:22`), but this is exactly the "weaken security for a test tool" shape the constraints rule out, and the client-count ceiling is better solved in Cognito.
